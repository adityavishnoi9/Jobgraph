The feature that exists today

A signed-in user saves a profile, connects one Gmail account through Google, and manually fetches messages matching a job-alert search. The Inbox page displays those fetched messages. There is no automatic profile relevance ranking in this request path.

Three actions to keep separate

  1. Connect: obtain permission and save a reusable credential. This does not fetch the job-alert list.
  2. Fetch: use that credential to search Gmail and load message details into Java memory.
  3. View: read the already-fetched messages from JobGraph’s API and render them in React.

1. Start in the browser

Connect Gmail opens a dialog. Continue with Google starts the server flow.

GmailConnectDialog uses a native dialog and focuses the email input. The form trims the address and calls onContinue. HTML validates email syntax; the backend also validates it. These checks do not establish ownership of the mailbox.

startGmailConnection sends JSON to POST /api/gmail/connect. The response contains an authorization URL. window.location.assign(url) navigates the browser to Google’s website; it is not an AJAX request to Google’s login screen.

Why an email field is not enough

Typing an address only tells JobGraph which mailbox the user intends to connect. Google handles sign-in, any verification challenge, and the permission screen. JobGraph does not send its own Gmail verification code and never asks the user to enter a Google password into this dialog.

After returning from Google

The URL result such as ?gmail=connected controls a UI notice. The component also calls GET /api/gmail/status for the saved connection. A success-looking URL alone is not proof that a connection exists.

2. Keep the user’s identity

Session authentication protects local API calls; CSRF protects state-changing requests.

Before a write, csrfToken() calls GET /api/auth/csrf if needed. It receives a token and the header name expected by Spring. The browser sends the session cookie with same-origin requests. Vite proxies /api to localhost:8080, so React normally uses relative URLs.

Login verifies credentials, rotates an existing session ID, puts the authenticated user in a SecurityContext, and explicitly saves it. It clears the previous CSRF token; the frontend clears its cached token too. A subsequent write obtains a fresh token.

CheckQuestion it answers
Session authenticationWhich JobGraph account is making this request?
Spring CSRF tokenDoes this write include the token expected for this session?
OAuth state, laterDoes Google’s callback match the connection attempt started in this session?

GET requests do not need Spring’s CSRF header here. The OAuth callback is a GET, so it uses the separate state validation shown on page 10. Public signup/login POST routes still require CSRF.[S1]

3. Create the OAuth attempt

The backend chooses the account from the authenticated session.

  1. Find the owner: accounts.current(authentication) resolves the logged-in account. The browser does not supply an accountId.
  2. Require a saved profile: the controller returns 409 if the profile does not exist.
  3. Create state: SecureRandom fills 32 bytes. URL-safe Base64 makes those bytes suitable for a redirect URL. Base64 is an encoding step, not encryption.
  4. Build Google’s URL: authorizationUrl() also checks that the encryption key is configured before redirecting the user.
  5. Save three session values: state, account ID, and requested email. These tie the future callback to this exact attempt.
Why these three values?

State connects the outbound and return trips. Account ID checks that the callback is still for the same JobGraph user. Requested email lets the backend compare Google’s confirmed mailbox with the address the user entered.

The values are one set of session attributes, so starting another connection in a second tab overwrites the first attempt. There is no separate OAuth-attempt timestamp or short expiry in this code; the attempt depends on session lifetime and removal during callback.

The complete connection trip

Follow the arrows once before reading the callback code.

Google returns the browser to the backend callback with a code and state. The browser’s JobGraph cookie allows the backend to recover the session that started the flow. The backend then talks directly to Google to exchange the code and identify the Gmail mailbox.

What the browser receives

It receives the authorization URL, the callback code/state while navigating, a redirect to /inbox, and connection status. JobGraph’s JSON APIs do not return the Google access token, refresh token, client secret, or encryption key.

5. Validate the callback

The callback can reach the controller anonymously, but attaching Gmail still needs the original login session.

SecurityConfig permits GET /api/gmail/callback so the controller can handle success, cancellation, and expired sessions. The controller immediately checks for a session and authentication; without them it redirects to /login?gmail=session-expired.

The callback reads all three saved values and removes them before proceeding. It compares the saved and returned state using MessageDigest.isEqual, checks the account ID, and requires the requested email. A mismatch returns /inbox?gmail=invalid-state without exchanging the code.

Then choose the outcome

  • If Google returned an error, or no code, redirect with gmail=cancelled.
  • If checks pass, call gmail.complete(account, code, requestedEmail).
  • After completion, clear that account’s old email stack and redirect with gmail=connected.
  • If the confirmed email differs, use gmail=email-mismatch. Other completion failures use gmail=error.
An attempt is consumed on return

Even a bad-state callback removes the saved attempt. Retrying the same callback URL will not complete that attempt. Begin again with Connect Gmail.

6. Exchange the code

The backend obtains tokens, then asks Gmail which mailbox those tokens belong to.

  1. Exchange: newTokenRequest(code).execute() contacts Google’s token endpoint using the configured client and callback URI.
  2. Create a client: gmailWithTokens receives the returned access and refresh tokens.
  3. Confirm identity: users().getProfile("me") reads the mailbox’s email address. Here ‘me’ means the user authorized by the Google credential.
  4. Compare: the confirmed address must equal the typed address, ignoring case. A login hint did not enforce this earlier.
  5. Ensure durable access: keep the new refresh token, or reuse the existing decrypted token only when reconnecting the same Gmail address.
Why reuse only for the same address?

A refresh token belongs to a particular authorization. Reusing mailbox A’s token while displaying mailbox B’s address would attach the wrong mailbox. A different mailbox without a new refresh token causes completion to fail.

The address comparison does not normalize Gmail dots, plus aliases, or every possible Workspace alias. A typed alias that differs from Google’s confirmed address can produce an email-mismatch result. Use the address Google confirms.

7. Save the connection

One database row connects a JobGraph account to one Gmail mailbox.

The service updates the existing row or creates a new GmailConnection. The database requires a unique, non-null account_id. That means an account has at most one saved Gmail connection; the saved profile and Gmail row both point to the account.

Database columnStored value
account_idThe JobGraph account owner; it is the lookup key used by the services.
gmail_addressThe address returned by Google’s Gmail profile API.
encrypted_refresh_tokenBase64 text containing the IV, encrypted refresh token, and authentication tag.
updated_atWhen JobGraph last saved/replaced the connection; this is not a token-expiry time.

GmailConnectionRepository extends JpaRepository, so save() persists the entity. findByAccount_Id(accountId) means lookup by the nested account.id property and returns Optional<GmailConnection>. The underscore makes the property traversal explicit.

A detail in the schema

gmail_address itself is not unique. The schema allows the same Gmail address to be connected to separate JobGraph accounts after each completes consent. Ownership checks still use account_id.

8. Protect the saved token

TokenCipher uses AES-256-GCM so the backend can recover the refresh token when needed.

The configured key is Base64-decoded and must be exactly 32 bytes: a 256-bit AES key. Every encryption generates a fresh 12-byte IV. GCMParameterSpec(128, iv) requests a 128-bit authentication tag. Java’s doFinal() produces encrypted bytes with the tag; the code prepends the IV and encodes the combined bytes as Base64.

During decryption, the first 12 bytes become the IV and the remaining bytes go through AES/GCM with the same key. A wrong key or changed encrypted value should fail authentication instead of producing a trusted token.

Encryption and hashing serve different needs

JobGraph must recover the refresh token to send it to Google, so it encrypts it. A login password is only checked for a match, so it is stored as a BCrypt hash. Base64 alone provides neither protection.

9. Obtain access when fetching

The saved refresh token lets the Google client obtain a usable access token.

gmailWithTokens(null, refreshToken) constructs GoogleCredential with the app’s client ID/secret and the decrypted refresh token. It intentionally starts with no access token. On the first outgoing request, the library’s Credential interceptor sees the missing access token and refreshes it, then adds the Bearer authorization header.

This behavior was checked in the installed google-oauth-client 1.36.0 source, Credential.intercept(), lines 195–207. The library can also refresh around expiry or authentication failure; the application does not implement its own refresh HTTP request.[J1]

Current caching behavior

getGmailService() creates a new client on each fetch call. The access token is reused within that client’s list/get operations, but there is no shared per-account access-token cache across fetch calls. The refresh token remains encrypted in the database.

Status, replacement, disconnect

A saved connection, an active login, and a valid Google grant are separate states.

connectedAddress() checks the local database and maps the connection to its address. It does not decrypt a token or contact Google. Therefore ‘Connected’ means a row exists; it does not prove the Google grant is still valid.

ActionWhat happens in the current code
Check statusGET /gmail/status returns connected=true plus the stored address, or false and null.
Change Gmail accountRun the same consent flow. The row is updated after address/token checks succeed; old fetched messages are then cleared.
Cancel replacementNo new connection is saved. The old saved connection remains.
DisconnectDELETE /gmail/connection deletes the account’s local connection row and clears its in-memory email stack.
Log outInvalidate the JobGraph session. The Gmail connection row remains for the next login.
Restart backendSaved connection rows remain in PostgreSQL. EmailStack’s in-memory messages disappear.
Local disconnect is not Google revocation

There is no call to Google’s revocation endpoint. Disconnect removes JobGraph’s saved token; the authorization grant may still appear in the user’s Google Account settings. An already-running request may also finish after disconnect.

10. Click Fetch job alerts

The backend searches the signed-in user’s connected Gmail account.

The frontend uses POST /api/emails/fetch with its session and CSRF header. AccountService derives accountId from authentication. The controller first checks that a local Gmail connection exists, then calls GmailFetchService. Results are pushed into the account’s stack, and the response reports counts.

The default search asks for recent messages with job-related subject words or matching senders. maxResults defaults to 10, and the controller clamps it to 1–50. The current button sends no custom query or limit. These are application choices, not Gmail’s maximum capabilities.

Fetching does not guarantee a relevant job

These search terms can include marketing, interview notifications, or unrelated messages. A From header is not proof of sender authenticity. This path does not perform profile matching, fraud checks, or AI scoring.

11. Search IDs, then read details

The Gmail API list call returns references; each get call supplies a message.

Java callConceptual REST request
messages().list("me")GET https://gmail.googleapis.com/gmail/v1/users/me/messages?q=…&maxResults=…
messages().get("me", id)GET https://gmail.googleapis.com/gmail/v1/users/me/messages/{id}
users().getProfile("me")GET https://gmail.googleapis.com/gmail/v1/users/me/profile (used during connection)

The list response provides IDs and thread IDs, so the loop requests each message separately. ‘me’ always refers to the Google user behind that client’s credential. Ten returned messages require one list call and ten detail calls, plus a token refresh when needed.[G3] [G4]

What the loop does and does not do

  • If getMessages() returns null, return an empty list.
  • Read detail requests sequentially, then convert each result to EmailDto.
  • Sort the fetched batch oldest to newest before passing it to the stack.
  • There is no nextPageToken loop, so this fetch reads one result page.
  • There is no partial-success handling: if one message fails, the method throws and the controller does not push this batch.

The code does not send a format parameter to messages.get. The API’s parsed message response supplies payload and headers used by the converter. The code never requests Gmail mutations such as marking a message read.

12. Turn MIME into readable text

An email can contain nested parts, alternative formats, and attachments.

extractBody first decodes data on the current part. Otherwise it looks for a direct text/plain child. If it finds none, it recursively checks children and returns the first non-empty body. The data is URL-safe Base64 and is decoded as UTF-8.

Practical limits of this parser

It does not download attachmentId bodies, combine every part, or inspect character-set declarations. The fallback can return HTML text or another part’s content. It prefers plain text among immediate children, but it is not a complete MIME normalization engine.

13. Keep each account’s messages

EmailDto is the API shape; EmailStack is temporary server memory.

The converter reads Subject and From headers, takes Gmail’s snippet and ID, extracts the body, and converts internalDate from milliseconds to LocalDateTime using the backend’s time zone. Jackson serializes the DTO getters into the JSON the frontend receives.

ConcurrentHashMap separates collections by account ID. computeIfAbsent creates the deque only when needed. ArrayDeque itself is not thread-safe, so operations on an account’s deque are synchronized. Before pushing a message, the code removes any existing item with the same Gmail message ID.

Two limits to understand

Only the incoming batch is sorted. A later custom search that fetches old messages can move those older messages above newer cached ones. Also, the cache has no size cap, expiry, or database persistence.

14. Show the messages in React

Fetching and displaying use two API requests.

The POST fetch response is a count object, not the message list. After it succeeds, onFetched() calls the handler supplied by InboxPage. That handler requests GET /api/emails/stack, puts the returned array into React state, and scrolls toward the message list.

How the Inbox page behaves

  • On opening, load the saved profile and the existing stack. A user without a saved profile is redirected to the workspace.
  • While loading, display a loading message; on failure, display the API error.
  • For each email, show subject, sender, received time, snippet, and an expandable body.
  • Disconnect clears the local React array after the backend removes the connection and stack.
Email text stays text

The body is inserted as a React text value. The component does not use dangerouslySetInnerHTML. HTML-looking email text is therefore escaped rather than executed or rendered as remote HTML. This also means some HTML-only messages may look unformatted.

What protects which boundary?

Security is several checks working together, each at a different point in the request.

Boundary / riskProtection in this code
Anonymous access to inbox APIsSecurityConfig requires authentication for /api/** except its explicit public routes.
Forged browser write requestsSession-backed Spring CSRF token on connect, fetch, disconnect, login, signup, and logout.
Callback attached to the wrong attemptRandom OAuth state, saved account ID, requested email, and session checks.
Typed address falsely claimed as ownedRead Google’s /users/me/profile result and compare the returned address.
Access to another JobGraph account’s dataDerive the account from Authentication; repository and stack calls use that account ID.
Database-only theft of a refresh tokenAES-GCM encryption with the key outside the database row.
Token exposure through frontend JSONReturn status/counts/messages, not the connection entity or token values.
Modifying Gmail accidentallyRequest gmail.readonly and call read methods only.
Email content executing as page HTMLRender message body through ordinary React text interpolation.

Cookie and origin settings

The current properties set HttpOnly=true, SameSite=Lax, and a 12-hour session timeout. HttpOnly blocks normal JavaScript reads of the cookie. SameSite=Lax is compatible with the top-level GET return from Google. The local configuration does not explicitly enable a Secure cookie; a deployed HTTPS setup should configure that.

CORS accepts the configured frontend origin plus the listed localhost/127.0.0.1 origins and permits credentials. CORS controls browser cross-origin access; it does not replace authentication or CSRF. The normal Vite proxy avoids cross-origin frontend API calls.

Encryption’s practical boundary

The running backend can decrypt the refresh token. If both the database and encryption key are compromised, the token can be recovered. The current cipher does not bind the encrypted value to account_id with additional authenticated data.

Local Google configuration

  1. Enable Gmail API in the Google Cloud project used by the OAuth client.
  2. Use a Web application OAuth client with the callback above registered exactly, including scheme, port, and path.
  3. Configure the consent screen and add the Gmail account as a test user if the app is in Testing.
  4. Start the frontend at localhost:5173 and backend at localhost:8080; sign in, save a profile, then connect.

Use localhost consistently during the trip. A session established for 127.0.0.1 is associated with a different host from localhost, so a callback to localhost may not recover that session. CORS permission alone does not share cookies between these hostnames.

Do not rotate the encryption key casually

The same saved ciphertext requires the original key. The current format has no key version or migration mechanism. Preserve the key across restarts; plan a token re-encryption or reconnection strategy before replacing it.

Diagnose fetch failures

A saved connection can still fail when the backend tries to use its credential.

SymptomMeaning and next check
409 Connect Gmail firstNo local connection row exists for the authenticated account.
502 Could not fetch Gmail messagesThe catch block wraps any fetch exception. Inspect the server cause: refresh failure, API response, network issue, parsing failure, or wrong encryption key.
Google invalid_grantA refresh token or code is unusable. During fetch, investigate revoked/expired access; reconnect after fixing the cause.
Google quota / permission responseCheck the original Google status and reason. The frontend 502 does not distinguish quota, API disabled, or insufficient permission.
Successful fetch, zero messagesCheck the actual query, date window, chosen Gmail account, and result limit. No matching messages is a normal empty result.
Messages disappear after restartEmailStack is memory-only. The saved Gmail connection can remain while cached messages are lost.
HTML-looking body or blank bodyInspect MIME parts. The parser may fall back to HTML text or lack attachment-backed body data.
Incorrect displayed timeThe backend converts to LocalDateTime and loses the timezone offset; the browser interprets that local-looking timestamp.

Why reconnect may be needed during development

Google documents that external apps in Testing can receive refresh tokens expiring after seven days when Gmail scopes are requested. Tokens can also stop working after revocation or other account/policy changes. A saved row does not prevent these provider-side changes.[G6]

Useful diagnostics without exposing credentials

  • Browser DevTools → Network: inspect method, path, status, response body, and whether the write included its CSRF header.
  • Backend log: locate ‘Gmail fetch failed for account …’ or ‘Gmail OAuth callback failed …’, then inspect the nested exception.
  • When sharing logs, omit cookies, authorization headers, token response bodies, secrets, and callback codes.

What this version does not promise

These observations come from the implementation, so you can plan the next steps accurately.

Current behaviorConsequence / a possible next step
Manual fetch only; no scheduler or push subscriptionNew mail appears only after a user fetches. Add a scheduled or event-driven sync if needed.
One list page and sequential detail callsLarge result sets are incomplete and may be slow. Add pagination and controlled batching/concurrency.
In-memory deque per app processNo durable inbox or multi-instance consistency. Persist messages with account and Gmail-connection ownership.
Only each incoming batch is sortedLater custom queries can disturb global newest-first order. Sort the merged collection or query a durable ordered store.
Disconnect and fetch are separate operationsAn in-flight fetch can repopulate the cache after clear/replacement. Bind writes to a connection version and reject stale results.
Status checks the database onlyA revoked grant can still look connected. Track reconnect-needed status after provider failures.
Simple MIME and local timestampsAttachment-backed bodies, encoding, and timezone cases need fuller handling.
One OAuth state slot; no dedicated TTLParallel connect tabs can invalidate each other. Store expiring attempts if multi-tab support is needed.
No Google revocation on disconnectThe Google grant can remain. Add explicit revocation if the intended disconnect semantics require it.
No profile-ranking call in this pathA fetched email is not a scored job match. Build the ranking stage as a separate, explicit step.

The code also does not add account ID as AES-GCM additional authenticated data, version encryption keys, configure a provider retry/backoff policy, or set an application-level fetch rate limit. These are design improvements, not claims that this guide implemented them.

Scope is still a meaningful limit

The current Google permission is read-only, but the backend has access to message contents. Treat those contents as user data throughout future filtering, storage, and AI processing.

  2. Confirm it reached the expected controller breakpoint. If not, inspect authentication, CSRF, CORS, or routing.

Do not confuse the two localhost services

The browser usually sends /api requests to Vite at port 5173, which forwards them to Spring at port 8080. Google’s registered callback goes directly to Spring at port 8080.

A complete example to rehearse

Fictional account 42 logs in with one email and connects a different Gmail mailbox.

  1. Login: dev@example.com authenticates to JobGraph. Spring stores its security context in the session. The account’s database ID is 42.
  2. Save a profile: the resume contact email may be contact@example.com. Neither that field nor the Gmail address replaces account ID 42 as the owner.
  3. Connect: enter career.mailbox@gmail.com. The server saves state S, account ID 42, and that requested address in the session.
  4. Consent: choose career.mailbox@gmail.com at Google. Google returns code C and state S through the browser to the callback.
  5. Validate: the session still belongs to account 42 and state matches. Remove the saved attempt; exchange C for tokens. Gmail’s profile endpoint confirms career.mailbox@gmail.com.
  6. Persist: encrypt refresh token R. Save account_id=42, the confirmed address, ciphertext, and updated_at. Redirect to /inbox?gmail=connected.
  7. Fetch: account 42 clicks Fetch job alerts. Decrypt R, let the Java client refresh an access token, search Gmail, and retrieve matching message details.
  8. Store and show: convert messages to DTOs, push them into stack[42], return counts, and let React GET /emails/stack to render them.
  9. Different user: account 99’s stack and repository lookup use 99. Supplying another person’s resume contact email does not change those lookups.
  10. Disconnect: delete account 42’s local Gmail row and clear stack[42]. The JobGraph account and saved profile remain.

Exercises with answers

QuestionAnswer
Does map(GmailConnection::getGmailAddress) update the row?No. It converts Optional<GmailConnection> to Optional<String>. An absent connection stays empty.
Why is connect POST, but callback GET?Connect creates server-side attempt state; Google returns through browser navigation to a validated callback.
Can we decrypt the password like the token?No. Passwords are hashed for comparison; refresh tokens are encrypted because they must be recovered.
